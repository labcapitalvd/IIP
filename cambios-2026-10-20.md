# Cambios del 20 de octubre de 2026

Resumen de lo realizado en la sesión de hoy: eliminación del simulador, administrador con usuario en base de datos,
conexión front ↔ Core/Auth ↔ PostgreSQL, rediseño de formularios, actualización (PUT), rutas por URL y módulo de Parámetros.

---

## 1. Simulador eliminado y administración separada de entidades

- Se eliminó todo el modo simulador/mock del front: `mockData.ts`, el interruptor «Modo de operación», los accesos rápidos de demo
  y el cambio de rol. El front solo habla con el backend real.
- Actores y sectores se cargan del backend tras el login; ya no hay datos de ejemplo.
- Se separó el portal en dos aplicaciones con diseño propio:
  - **Administración** (`AdminApp`): barra lateral propia.
  - **Entidades** (`EntityApp`): conserva el diseño anterior. *Pendiente de rediseñar.*
- Se quitó el botón «Diligenciar IIP» (el admin ya no «entra como entidad»).

## 3. Conexión front → Core/Auth → base de datos

Causas del «Failed to fetch» y correcciones:

1. Nginx del backend quedaba con IP viejas de `auth`/`core` (502). Hay que reiniciarlo si se recrean (`docker restart app_nginx`).
2. El navegador enviaba `X-Platform: mobile`, que el backend rechaza si hay `Origin`. Ahora usa `web` (refresh token en cookie `httpOnly`).
3. CORS con credenciales y orígenes explícitos en desarrollo (`localhost:4287`, `localhost:3000`).
4. SQLAlchemy 2.1 ya no instala `greenlet`: `shared` ahora depende de `sqlalchemy[asyncio]`.
5. Base vacía: se ejecutaron schemer, migraciones y seeder.
6. El certificado autofirmado bloqueaba el `fetch` entre orígenes. **Solución final:** el nginx del front hace de proxy
   (`/api/auth/*` → Auth, `/api/core/*` → Core). Mismo origen: sin CORS ni certificados. Vite hace lo mismo en `npm run dev`.
7. Tokens: el backend devolvía 500 con token vencido; ahora responde **401** y el front **renueva el token solo** y reintenta.

> Imágenes de Docker Hub ≠ datos: la base de datos vive en el volumen `pg` de cada máquina y `Secrets/`/`.env` no viajan en la imagen.
> En otro servidor hay que correr migraciones + seeder y definir sus propios secretos.

## 4. Nueva estructura de formularios

**Formulario → Variables → Indicadores → Preguntas**

- **Variable** e **Indicador**: nombre, descripción, ayuda e ícono (18 íconos).
- **Preguntas simples**: texto, numérica, selección única, selección múltiple, Sí/No y **archivo**.
- **Pregunta bucle**: tarjeta repetible con campos propios (texto, número, fecha, Sí/No, selección, archivo), cada uno con
  su texto de ayuda. Puede depender de una pregunta Sí/No del mismo indicador (ej.: 1.1 aparece solo si la 1 es «Sí»).
  La numeración (1, 1.1, 2…) es automática.
- **Pregunta de archivo**: el admin elige los tipos de archivo permitidos y el tamaño máximo (no puede superar el límite del tipo).
- Los formularios con el formato anterior (Dimensión → Criterio) se convierten solos al abrirlos.
- El portal de entidades sigue con el diseño anterior (lista plana por variable, sin bucles condicionales). *Pendiente.*

### Backend de formularios
- Migraciones nuevas: `5b1c9d2e7a10` (`forms.sections.icon`) y `6c2d0e3f8b21` (`forms.forms.updated_at`).
- Seeds nuevos: tipos de sección (C/V/I) y tipos de regla `file_types` y `max_file_size`.
- Condiciones de bucle → `rules.field_dependencies`; tipos y tamaño de archivo → `rules.field_rules`.
- Corregido: las secciones hijas se guardaban sin `form_id`.

## 5. Actualizar formularios (PUT)

- `PUT /public/forms/{form_id}` reemplaza la estructura.
- **Regla:** si el formulario ya tiene respuestas → `409 FORM_HAS_SUBMISSIONS_ERROR`, no se modifica nada, y el front avisa
  antes de abrir el editor.
- Al guardar: loader que **bloquea** el editor → alerta «Formulario guardado correctamente» → vuelve a la lista y **recarga**
  la pantalla (evita dobles `PUT`).
- El pie del editor muestra la **fecha de última actualización** confirmada por el servidor.
- Validación con alerta: lleva al indicador/pregunta con el problema y lo resalta.
- Un formulario nuevo con un código ya existente en el servidor ya no sobrescribe en silencio.

- Cada rol solo ve lo suyo (admin ↔ `/admin`, entidad ↔ `/entidad`).
- Con el access token vencido o ausente (pestaña nueva) la sesión se restaura sola con la cookie.

## 7. Parámetros (CRUD de tablas de apoyo)

Menú **Parámetros** → `http://localhost:4287/admin/parametros`. Solo administradores (otros usuarios reciben 403).
El borrado se **bloquea si el valor está en uso** (muchas FK de la base son `ON DELETE CASCADE`).

| Grupo | Tabla (URL) | Tabla en BD | Operaciones |
|---|---|---|---|
| Entidades | Sectores · `/admin/parametros/sectores` | `actors.actor_segments` | Crear, editar, eliminar |
| Formularios | Tipos de sección · `/admin/parametros/tipos-seccion` | `forms.section_types` | Solo editar textos |
| Formularios | Tipos de campo · `/admin/parametros/tipos-campo` | `reference.field_types` | Solo editar textos |
| Formularios | Tipos de archivo · `/admin/parametros/tipos-archivo` | `reference.file_types` | Crear, editar, eliminar |
| Formularios | Operadores relacionales · `/admin/parametros/operadores` | `reference.relational_operators` | Solo editar textos |
| Formularios | Tipos de regla · `/admin/parametros/tipos-regla` | `reference.rule_types` | Solo editar textos |
| Radicados | Estados de radicado · `/admin/parametros/estados-radicado` | `reference.submission_status_types` | Crear, editar, eliminar |
| Interacciones | Tipos de comentario · `/admin/parametros/tipos-comentario` | `reference.comment_types` | Crear, editar, eliminar |
| Interacciones | Tipos de notificación · `/admin/parametros/tipos-notificacion` | `reference.notification_types` | Crear, editar, eliminar |
| Seguridad | Tipos de acción de auditoría · `/admin/parametros/tipos-accion-log` | `reference.log_action_types` | Crear, editar, eliminar |
| Seguridad | Roles de sistema · `/admin/parametros/roles-sistema` | `reference.system_roles` | Crear, editar, eliminar |
| Seguridad | Roles sobre recursos · `/admin/parametros/roles-recurso` | `reference.resource_roles` | Crear, editar, eliminar |
| Seguridad | Permisos · `/admin/parametros/permisos` | `reference.permissions` | Solo editar textos |

«Solo editar textos»: son catálogos cuyo código tiene lógica en el sistema; el código no se puede cambiar ni crear/borrar registros.
En el resto, el código queda bloqueado después de crear el registro.

## 8. Endpoints nuevos o modificados (Core)

Base: `http://localhost:4287/api/core/public` (vía proxy del front) o `https://localhost:4289/public` (directo, certificado autofirmado).

| Método | Ruta | Uso |
|---|---|---|
| POST | `/forms` | Crear formulario |
| **PUT** | `/forms/{form_id}` | Actualizar formulario (409 si tiene respuestas) |
| GET | `/forms/lookup/{code}` | id, última actualización y si tiene respuestas |
| GET | `/forms/file-types` | Tipos de archivo disponibles |
| GET | `/parameters` | Catálogo de tablas parametrizables |
| GET | `/parameters/{tabla}` | Registros de una tabla (con conteo de uso) |
| POST | `/parameters/{tabla}` | Crear registro |
| PUT | `/parameters/{tabla}/{id}` | Actualizar registro |
| DELETE | `/parameters/{tabla}/{id}` | Eliminar registro (409 si está en uso) |

## 10. Para aplicar en otro entorno

```bash
docker compose build base            # primero la base
docker compose build auth core persister frontend
docker compose run --rm persister sh -c "cd /api/migrator && alembic upgrade head"
docker compose run --rm persister sh -c "cd /api/seeder && python seeder.py"
docker compose up -d
docker restart app_nginx
```
